# Boston Control Center — QA Report

**Date:** Friday, August 14, 2026, 14:16–14:35 ET (19 min session)
**Target:** https://boston-control-center.vercel.app (production, authenticated)
**Tester persona:** Boston Globe newsroom member, desk editor
**Method:** Live browser exploration across all tabs, DOM inspection, console monitoring, interaction testing, code review against UI state

---

## Executive Summary

The dashboard is genuinely impressive — a real-time, audio-backed public safety map with more depth than most in-house tools newsrooms build for themselves. It is also **production-fragile in ways that will silently erode newsroom trust**. 432 unhandled JavaScript errors accumulated during a 19-minute session. The recurring error fires every few seconds on every tab. A reporter who opens browser DevTools sees a wall of red. The code comments show high engineering intelligence; the runtime shows an unruly ship.

**12 issues found:** 2 Critical, 4 High, 3 Medium, 3 Low.

## What Works (the good parts, said plainly)

1. **Real radio is flowing.** Boston Police, Cambridge Fire/Police, Mass State Police, MBTA, MIT, Needham/Brookline, Melrose Fire all streaming transcripts. 33,478 transmissions processed, 2,108 incidents formed, 65 active. Audio clips stored in Vercel Blob with real, accessible URLs. This is not a demo — it is built and running.

2. **Situation cards are genuinely good.** "Medical emergency at 850 Boylston St. — anaphylactic reaction" is tight, editorial, accurate. The `hear it unfold (4)` button is the right idea. Beat count shows live attention.

3. **STOPS tab is a real product.** "3 out now / 13 tonight / median 14:04 / longest 14:04 C3 / plate read 2 / arrests 1 / searches 0 / never cleared 11" is a morning meeting number. The ON THE MAP link is exactly right. The legal caveat reads correctly.

4. **ARCHIVE tab parses natural language well.** "big fire last night in Back Bay" → type:fire, in:back bay, serious calls first, tonight (Aug 14 6PM–Aug 15 6AM). 0 results because the archive is new. That is honest.

5. **DESK view is a real assignment desk**: On the Board (2), Live Map (39 routine calls last hour), Coming In (57 waiting), On the Air (live feed). This is what a city editor at 3pm needs.

7. **Audio pipeline is architecturally sound.** CLIP_PLAYER is a single shared Audio element, event delegation for clicks, CLIP_Q for radio mode, RADIO_SEEN prevents replays. The code comments explaining the dial paint state logic are excellent.

## Critical Issues

### 1. TypeError: Cannot set properties of null — every 4 seconds, 432 times in 19 minutes

**Severity:** Critical
**Category:** Console / Functional
**Evidence:** 432 identical unhandled promise rejections captured in `window.__qaErrors`.

```
REJECT: TypeError: Cannot set properties of null (setting 'textContent')
```

**Impact:** Something in the poll loop polls a DOM element that no longer exists (or was never created in this tab's state). The error is not fatal to rendering — the page works — but it means:
- The browser's `window.onerror` fires constantly, adding noise
- If Sentry or error reporting is ever added, this drowns real errors
- Dev console looks broken to a reporter who opens it
- The interval keeps burning CPU cycles on dead work

**Root cause hypothesis from code reading:** `pollConsole()` at line 2351 updates `#consoleSub`. If `consoleSub` is missing (e.g., on certain tab views), `sub.textContent` throws. The guard `if(sub)` exists at lines 2381–2384 for `consoleSub` but not for all elements. The 4-second interval matches the refresh cadence seen in the UI.

**Recommendation:** Add a null check for every element this loop touches, or close the interval when the relevant tab is not active.

### 2. Keyboard navigation: Tab key does not move focus anywhere

**Severity:** Critical
**Category:** Accessibility / Functional
**Evidence:** 14 tab presses; focus stayed on `BODY` every time.

**Impact:** A newsroom member who depends on keyboard navigation cannot use this tool. Not "hard to use" — cannot use. Editors with RSI, motor impairments, or screen-reader reliance are locked out. This is also a legal exposure for a large media company.

**From the docs (AGENTS.md):** The team knows. `#149 Keyboard reachability` acknowledges zero `tabindex`, zero `aria-` attributes across nine layer switches, feed rows, situation cards, stop rows, console hit lines, and both close boxes. The tabs are `<button>` elements with `onclick` but no `role`, `tabindex`, or `aria-selected`.

**The fix per AGENTS.md:** "The intended pattern is roving tabindex: the container is the single tab stop, rows are `tabindex="-1"`, arrow keys move, Enter activates." That pattern is documented. It is not implemented.

**Recommendation:** This should be the first ticket after the store is stable. It is not polish; it is an entry requirement for the tool.

## High Issues

### 3. The `2 of 12 offline` badge has no detail — a desk editor cannot act on it

**Severity:** High
**Category:** UX / Content
**Evidence:** HUD shows `2 of 12 offline` persistently. Clicking it does nothing. No tooltip, no modal, no link to Under the Hood.

**Impact:** An editor who sees this alarm cannot answer the first question: *which feeds?* The answer requires navigating to Under the Hood. A non-technical editor may not know that view exists. The badge looks broken — "2 of 12 offline" with no name or timestamp.

**Real data during test:**
- Boston Fire: `offline · never connected`
- Lowell Police: `offline · last audio 17h ago`

**Recommendation:** Make the badge a click-through to Under the Hood feeds section, or add a tooltip on hover listing the offline feeds by name.

---

### 4. Scene-summary model: 22.5% failure rate (9 of 40 calls failing, 2514ms avg)

**Severity:** High
**Category:** Functional / Console
**Evidence:** Under the Hood, Models section: `MODELS 9 of 40 calls failing` with `scene-summary 40 (9 failed)` at `2514ms avg`.

**Impact:** The cards on the board are written by this model. Nearly one in four calls fails. The ones that succeed take 2.5 seconds. For a newsroom desk watching breaking news, that is both slow and unreliable. The consequence is brief and low-quality situation summaries, or missing summaries entirely.

**Current model:** `deepseek/deepseek-v4-flash-0731` (visible in the model log, different from the lib code docstring which references OpenRouter/inclusionai). The code comment in `extractor.js` says: *"DeepSeek's flash burned the whole 20-second budget without answering"* — the measurements are known, and the current implementation reflects them.

**Recommendation:** The `cap 6000/day` on extract is correct budgeting, but summarize what drives the failure rate. If it is timeouts, shorten the timeout and degrade gracefully. If it is parse errors, capture them and adapt the prompt. This is the quality line between "useful tool" and "annoying toy."

---

### 5. Geocoding failure: `GEOCODE no map match` appears in over 70% of live extractions

**Severity:** High
**Category:** Functional / Content
**Evidence:** Under the Hood EXTRACT section shows `units: A3 / type: —` and GEOCODE section shows `no map match` repeatedly. Extractor pulls units but `type` is `—` for most calls, and geocoding fails for everything except the ones with an explicit city name (e.g., "Cambridge").

**Impact:** The map is the product. If 70% of calls cannot be placed, the map is a sparse sampling of reality, not a live picture. The extractor's docstring acknowledges: *"Measured on 150 live transmissions: 114 of them produced no location field at all."* This is the 75% empty map problem.

**From the code:** `lib/extractor.js` — the schema accepts a bare street name or town. But Under the Hood shows the regex path firing for most calls (the `type: —` pattern) rather than the model path. The OpenRouter model appears to be timing out or declining to answer, falling back to regex, which only extracts units it hears explicitly.

**Recommendation:** This is the single biggest lever for newsroom value. Either the model layer needs to answer faster/more reliably, or the regex path needs to expand its vocabulary for type (MVA = traffic crash, 10-54 = medical aid, etc.). A type-empty extraction should not post to the queue.

### 6. Audio playback: Click-to-play produces no audio element — user gesture may be required but not requested

**Severity:** High (suspect; evidence is consistent)
**Category:** Functional
**Evidence:** Clicked `.cplay` buttons directly via JS (`btn.click()`). No `<audio>` element appeared in DOM. `CLIP_NOW` stayed empty. No error raised.

**Analysis of the code:** `clipPlay(url)` at line 2195 calls `p.play().catch(()=>{clipStop();clipNext();})`. If the browser blocks the play (autoplay policy) because the click was not a genuine user gesture, the error is swallowed silently. The function returns `true` but nothing plays.

**Impact:** A reporter who presses a play button expects to hear the radio. If the click is generated programmatically (as in testing), the experience is silent with no feedback. If this can happen in real use (e.g., a keyboard-triggered activation that the browser does not classify as a user gesture), it is a silent failure.

**Recommendation:** The `catch` at line 2208 should set a visible error state on the button or the dial, not silently advance the queue. `clipStop()` after a failed play makes it look intentional.

## Code observations (not bugs, but notable)
